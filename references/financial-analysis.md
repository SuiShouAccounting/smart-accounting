# 财务分析子场景

## 何时读这个文件

当用户问"花了多少/赚了多少/结余/流水/对比/趋势/占比/分布"等涉及**统计汇总**的问题时阅读此文件。

## 三类查询的判断与对应 api_name

| 用户意图 | api_name | 示例 |
|---------|----------|------|
| 看具体流水 | `list_transactions`（明细） | "最近7天流水" |
| 看整体指标 | `get_transaction_summary`（汇总） | "本月消费多少" |
| 看分组对比 | `get_transaction_group_summary`（分组） | "各项支出占比" |

调用时 `biz_type` 取默认账本 type，`book_id` 取默认账本 id。

## 输出规范（重要）

**所有财务分析结果必须在末尾附时间范围备注**，作为小字提示，让用户清楚数据覆盖的时间区间。

- 格式：`> 时间范围：YYYY-MM-DD 至 YYYY-MM-DD`
- 位置：结果正文末尾，单独一行，使用 `>` 引用块
- 时间范围来自**实际换算**的结果，不是用户原始输入
- 如果用户用的是相对时间（如"本月"），备注里写换算后的绝对日期
- **多分组/多分类/多账户的结果一律用 Markdown 表格输出**（表头 + `| -- |` 分隔行 + 数据行），与 `references/output-rules.md` 的强制表格规范一致，任何平台都不得降级为纯文本、顿号串、或仅文字描述

**示例**：

```
本月支出分布：

| 分类 | 支出 | 占比 |
|---|---|---|
| 休闲娱乐 | 1860.00 | 62% |

> 时间范围：2026-07-01 至 2026-07-31
```

## 时间筛选写法（推荐固定命令 query + 瞬态参数文件，命令串恒定）

> **财务分析统一用 `call_gateway.py query` 固定命令**，具体接口与筛选通过瞬态参数文件 `sui_cache.json` 的固定 JSON 结构 `{"api_name":"...","params":{...}}` 传递。命令串 `python3 scripts/call_gateway.py query` 永远不变（可被平台记忆放行），所有易变数据都在参数文件里，不进命令行。

### 时间写法：口语自动归一化，标准格式永远可用（重要）

**脚本会先将常见口语表达归一化为标准格式**，再转毫秒。可以直接传用户原话，也可以自行换算后传标准格式，两种方式均可。

**标准格式（三种）**：

| 格式 | 含义 | 示例 |
|------|------|------|
| `YYYY-MM-DD` | 单日 | `2026-09-20` |
| `YYYY-MM-DD HH:MM` | 精确时刻 | `2026-09-20 10:00` |
| `YYYY-MM-DD~YYYY-MM-DD` | 日期区间（含首尾） | `2026-09-01~2026-09-30` |

**口语说法自动归一化（常见说法都支持，直接传原话即可）**：

| 用户说法 | 归一化结果 |
|------|------|
| "9月20号上午" | `2026-09-20 10:00` |
| "9月20号" / "9月20日" | `2026-09-20` |
| "昨天" / "昨天下午" | `2026-10-22` / `2026-10-22 15:00` |
| "前天" / "大前天" | `2026-10-21` / `2026-10-20` |
| "上午"（无日期） | `2026-10-23 10:00`（按今天） |
| "20号" | `2026-10-20`（按当月） |
| "本月" / "上个月" | `2026-10-01~2026-10-31` / `2026-09-01~2026-09-30` |
| "本周" / "上周" | `2026-10-19~2026-10-25` / `2026-10-12~2026-10-18` |
| "今年" / "去年" | `2026-01-01~2026-12-31` / `2025-01-01~2025-12-31` |
| "最近7天" / "最近" | `2026-10-17~2026-10-23` / 近 15 天 |
| "9月1号到9月20号" | `2026-09-01~2026-09-20` |

**时段词会落成具体时刻**：凌晨 03:00、清晨 06:00、早上 08:00、上午 10:00、中午 12:00、下午 15:00、傍晚 18:00、晚上 20:00、夜里 22:00、深夜 23:00。

**归一化失败时**（如"国庆那几天""上上周末"这类需要外部日历知识的说法）：
- 脚本**直接报错、不提交**，并在错误信息里回显标准格式
- 此时**自行换算**成标准格式重发，**不得回退为"今天"**（会把历史账记错日期）
- 例："国庆那几天" → 换算为 `2026-10-01~2026-10-07` 后传入

> **换算依据**：当前日期以系统时间为准。无年份的月日若明显在未来，会回退一年/一个月（"9月20号"在 10 月说 → 当年 9 月 20 日）。
>
> **区间分隔符**兼容 `~`、`至`、`到`，推荐用 `~`（不会被误认为日期里的连字符）。
>
> 用户**未提及时间**时不传 `time` 字段（查询默认整账本，记账默认当前时刻），不要自行补充。

```bash
# 首选：瞬态参数文件——Write sui_cache.json（当前工作目录 os.getcwd()，平台无关）：
{"api_name":"get_transaction_summary","params":{"time":"上个月"}}
# 也可以直接传标准格式：
{"api_name":"get_transaction_summary","params":{"time":"2026-09-01~2026-09-30"}}
# 然后跑固定命令（Windows 同句，python3 改 python）：
python3 scripts/call_gateway.py query
```

> 用户只说"最近"不加天数 → 默认按 15 天，**不要追问**。
> 时间已由脚本换算并作为 `start_time`/`end_time` 传给网关。**这些毫秒值是脚本内部传参用，绝不回显给用户**；展示时按 `references/output-rules.md` 的时间戳规范转成 `YYYY-MM-DD`。
> 若需要跨月自定义精确区间，`time` 写绝对区间即可（如 `"2026-07-01到2026-07-31"`），不必手拼毫秒值。

## 场景 1：汇总查询（get_transaction_summary）

返回 `data` 含 `income` / `expense` / `balance`。`measures` 不传时默认整账本收支结余。

请求示例：
```bash
# Write sui_cache.json：
{"api_name":"get_transaction_summary","params":{"time":"本月"}}
# 不带 time 默认整账本；跨月自定义区间：time 写绝对区间
# {"api_name":"get_transaction_summary","params":{"time":"2026-07-01到2026-07-31"}}
# 然后跑固定命令：
python3 scripts/call_gateway.py query
```

### 样例
```
用户：查询下最近10天消费多少钱

模型：最近 10 天共消费 **2456.90 元**。

> 时间范围：2026-07-18 至 2026-07-27
```

✅ **关键点**：用户问什么答什么，不要把收入、结余一起报。

```
用户：本月一共收支多少、记账多少笔？

模型：
### 本月收支
收入 8500.00 元，支出 3265.40 元，结余 5234.60 元。

> 时间范围：2026-07-01 至 2026-07-31
```

> 若需记录笔数，可结合 `get_transaction_group_summary` 的 `RECORD_COUNT`，或 `list_transactions` 拉总数。

## 场景 2：分组统计（get_transaction_group_summary）

`group_by` **必填**，`measures` 指定要统计的指标。网关返回分页的 `items`，按 `group_key`/`group_name` 分组。

**分组维度（group_by）**，不可自行编造：

| 维度 key | 含义 | 维度 key | 含义 |
|---------|------|---------|------|
| `TIME_DATE` | 按日 | `CATEGORY_FIRST` | 按一级分类 |
| `TIME_WEEK` | 按周 | `ACCOUNT` | 按账户 |
| `TIME_MONTH` | 按月 | `PROJECT` | 按项目 |
| `TIME_QUARTER` | 按季 | `MEMBER` | 按成员 |
| `TIME_YEAR` | 按年 | `MERCHANT` | 按商家 |
| | | `USER` | 按记账人（**仅 SXY 账本；SSJ 账本不支持，改 ACCOUNT/CATEGORY_FIRST 等其它维度**） |

**指标（measures）**，不可自行编造，**只允许下表 6 个**（其它指标名不支持——不要尝试）：

| 指标 key | 含义 | 指标 key | 含义 |
|---------|------|---------|------|
| `EXPENSE` | 支出金额 | `RECORD_COUNT` | 记录总数 |
| `INCOME` | 收入金额 | `EXPENSE_COUNT` | 支出记录数 |
| `BALANCE` | 结余 | `INCOME_COUNT` | 收入记录数 |

请求示例（分组统计，Write 固定参数文件 + 固定命令）：
```bash
# Write sui_cache.json：
{"api_name":"get_transaction_group_summary","params":{"time":"本月","group_by":"TIME_MONTH","measures":["INCOME","EXPENSE","RECORD_COUNT"],"page":1,"page_size":30}}
# 然后跑固定命令：
python3 scripts/call_gateway.py query
```

响应 `data`：`group_by` + `items[]`（每项含 `income`/`expense`/`record_count` 等指标 + `group_key`/`group_name`）+ 分页字段。**展示时用表格 + 占比 + 业务洞察**。

### 样例
```
用户：本月钱都花在哪了？

模型：本月支出分布：

| 分类 | 支出 | 占比 |
|---|---|---|
| 休闲娱乐 | 1860.00 | 62% |
| 食品酒水 | 835.50 | 28% |
| 行车交通 | 311.00 | 10% |
| **合计** | **3006.50** | 100% |

其中一笔休闲娱乐支出占比较高，属于异常大额消费，建议关注。

> 时间范围：2026-07-01 至 2026-07-31
```

✅ **关键点**：表格 + 占比列 + 结尾业务洞察。

## 场景 3：流水明细（list_transactions）

> **重要原则**：流水明细数据量通常很大，**不要主动建议用户查明细**。只有当用户**明确要求**（如"看流水"、"查明细"、"列出每笔"）时才使用。对于"花了多少/赚了多少"这类问题，用汇总或分组即可。

请求示例（流水明细，Write 固定参数文件 + 固定命令）：
```bash
# Write sui_cache.json：
{"api_name":"list_transactions","params":{"time":"最近7天","page":1,"page_size":20}}
# 按分类筛明细：
# {"api_name":"list_transactions","params":{"time":"本月","category_ids":["<分类ID>"]}}
# 然后跑固定命令：
python3 scripts/call_gateway.py query
```

**支持的分页与筛选参数**（可组合）：

| 参数 | 说明 |
|------|------|
| `page` / `page_size` | 分页（page 默认 1；page_size **上限 50**，超过会被服务端自动调整为 50，无需处理） |
| `category_ids` | 按分类筛选（数组） |
| `account_ids` | 按账户筛选（数组） |
| `member_ids` / `merchant_ids` / `project_ids` | 按基础资料筛选（数组） |
| `trade_type` | 按类型筛选，**两线统一传大写**：`Expense`/`Income`/`Transfer`/`Refund`/`Balance_Changed`（SSJ 也接受小写，但统一用大写最稳。SSJ 账本没有退款流水，**不要对 SSJ 用 `Refund` 筛选**——会报错） |
| `start_time` / `end_time` | 按时间区间筛选（毫秒时间戳，字符串；end 不得早于 start） |
| `keyword` | 按备注模糊搜索 |

响应 `data`：`items[]`（流水列表）+ `page` / `page_size` / `has_more`。每条流水含 `transaction_id`、`trade_type`、`from_amount`/`to_amount`、`transaction_time`、`remark`、账户/分类（含名称）等。

> 流水固定按记账时间倒序。`has_more` 为 true 时可翻下一页。

### 样例
```
用户：查询下最近7天的流水详情

模型：最近 7 天共 **15 笔**流水（按时间倒序）：

### 收入 3 笔
| 日期 | 备注 | 分类 | 金额 |
|---|---|---|---|
| 7月25日 | 工资 | 工资收入 | +1000.00 |

### 支出 12 笔
（略）

**小计**：收入 2000.02 元，支出 2860.35 元，结余 -860.33 元。

> 时间范围：2026-07-21 至 2026-07-27
```

✅ **关键点**：收入/支出分组展示、按时间倒序、末尾业务总结。

## 场景 4：对比分析

### 样例：环比对比
```
用户：相较上个月，这个月多花了哪些钱？

模型：上个月（2026年6月）没有记账数据，所以无法做两月对比。但我可以分析本月支出结构，给你优化建议：

### 本月支出分布
（表格）

> 时间范围：2026-07-01 至 2026-07-31
```

✅ **关键点**：数据不足时**诚实告知**，但主动给出**基于现有数据的建议**，不要直接说"无法分析"。

❌ **反例**：数据不足时硬编造——"本月比上月多花了 2000 元..."（上月没数据，不能编造）。

## 边界场景

### 时间范围过大导致数据量爆炸
```
用户：查询最近10年的所有流水
（可能上万条）

模型：10 年的流水可能有上万条，全量返回会比较慢。
你关心的是哪方面？比如：每年支出汇总、某年的明细、特定分类的历史？
```
✅ **规则**：明细查询数据量可能爆炸时，**主动建议改用汇总或分组**，而不是硬查（服务端每页最多 50 条，翻页也不会一次拉爆，但翻很多页同样没必要）。

### 查询结果为空
```
用户：昨天花了多少钱
（昨天没有任何流水）

模型：昨天（2026-07-19）没有记账记录。

> 时间范围：2026-07-19 至 2026-07-19
```
✅ **不要假装有数据**，也不要暴露"返回空数组"。用业务语言说"没有记账记录"。
