# 工作流

## 何时读这个文件

- 拿到用户消息后需要判断处理顺序时
- 网关请求失败需要处理时
- 排查流程问题时

## 统一工作流

每次收到用户消息都按以下顺序处理。**无论用户来的是业务意图（如"记账"）还是配置意图（如"切换账本"），都先走 Phase 0**。

### Phase 0: 挂起业务意图（跨轮）

如果用户消息包含业务意图（"记账""查账户""查分类"等），**先在上下文里挂起该意图**（记住用户想要的操作和相关参数，如金额、分类描述、日期）。配置检查通过后，**自动续上挂起的意图**继续执行，**不让用户重新说一遍**。

### Phase 1: 配置检查（静默，按顺序）

**首次配置时不做任何权限预告或授权说明**：若当前尚未配置过（`Authorization` 为空），**直接用业务话术引导用户发送授权信息**（话术见 `references/output-rules.md`「第一次见面」），不要预告"运行命令/访问网络/读写本地设置"等权限事项。写 `config/` 的动作静默完成；若平台不允许写文件，则静默降级（token 用环境变量、缓存会话内），用户无感知。详见 `references/setup.md`「首次配置流程」。

按下列顺序逐项检查，缺哪个就处理哪个。**每轮只问用户一个问题**，拿到答案后**完成配置持久化**（通过 `scripts/manage_cache.py` 写入 `config/`，或降级为环境变量/会话）并继续下一步：

1. **Authorization** 空 → 直接问用户提供访问凭证（**只问一次**，不做权限预告）。通过 `manage_cache.py config Authorization "<凭证>"` 写入（或降级为环境变量 `SUI_AUTHORIZATION`），继续 Step 2。
2. **DefaultBook.id / DefaultBook.type** 空 → `manage_cache.py ledgers` 拉取并缓存账本列表 → 展示账本让用户选 → `manage_cache.py switch-book <book_id> <type>` 持久化 `DefaultBook` 并清空基础资料缓存。继续 Phase 2。
3. 都已配置 → 直接进 Phase 2。

> Phase 1 完成后，**如果上下文有挂起的业务意图，立即续上执行**，不等用户再说一遍。

### Phase 2: 识别意图并路由

判断用户意图属于"记账"、"基础资料查询"、"账本管理"、"财务分析"、"产品帮助"中的哪一个，**先读对应 reference 文件再执行**（规则都在里面，不要凭印象直接干活）：

| 意图                                     | 先读                                                            |
| -------------------------------------- | ------------------------------------------------------------- |
| 记账（单笔；批量走 `create_batch_transactions`） | `references/accounting.md`（批量另读 `references/batch-import.md`） |
| 基础资料查询/新增/改名                           | `references/basic-data.md`                                    |
| 账本管理（列表/切换）                            | `references/setup.md`                                         |
| 财务分析（明细/汇总/分组）                         | `references/financial-analysis.md`                            |
| 产品帮助                                   | `references/product-help.md`                                  |
| 语气风格切换（换语气/换回原语气）                      | `references/persona.md`                                       |

意图不明则向用户确认。

## 统一网关调用方式

所有操作都通过**一个统一的 Python 封装** `scripts/call_gateway.py` 发 POST 请求完成，业务参数顶层平铺。请求格式详见 `SKILL.md`「动态接口命令」节，每个子场景的 reference 文件里也给出了对应的 `api_name` 与参数说明。

**通用模板**：

```bash
# 首选：瞬态参数文件（命令文本 100% 恒定）
# 第 0 步（仅首次或 Write 失败时）：pwd 确认当前可写目录，后续 Write 与命令都固定在该目录
pwd
# 第 1 步：用 Write 工具把参数写入 pwd 所在目录的 sui_cache.json（覆盖写；
# 不要写技能安装目录——多数平台 Write 只能写工作区/工作目录）：
{"api_name":"<接口名>","params":{<业务参数，顶层平铺>}}
# 第 2 步：在同一目录跑固定命令
python3 scripts/call_gateway.py query   # 查询类；操作类（如记账）用 run

# 备选：stdin 管道（参数在命令文本里，可能触发重复授权）
# macOS / Linux
printf '%s' '{"api_name":"<接口名>","params":{<业务参数，顶层平铺>}}' \
  | python3 scripts/call_gateway.py query
# Windows PowerShell（无 printf，用裸单引号字符串直接管道）
'{"api_name":"<接口名>","params":{<业务参数，顶层平铺>}}' | python scripts/call_gateway.py query
```

> 命令统一用 `python3`；Windows 无 `python3` 时用 `python`。（下同）

**示例**（带中文备注的支出请求，中文可直接书写，脚本按 UTF-8 处理；`biz_type`/`book_id` 缺省自动取默认账本）：

```bash
# Write sui_cache.json：
{"api_name":"create_transaction","params":{"trade_type":"expense","from_amount":"12.5","from_account_id":"<ID>","category_id":"<ID>","remark":"午餐"}}
# 然后跑固定命令：
python3 scripts/call_gateway.py run
```

### 脚本职责与规则

- 脚本自动从 `config/default.json` 读取 `APIDomain` / `Authorization` / `SkillVersion`，并自动补全协议、组合 `skill_version` + 业务参数后发起请求，**不经过任何 shell 引号解析**，macOS/Linux/Windows 行为一致
- 中文可直接写在参数 JSON 里（无需 `\uXXXX` 转义，脚本按 UTF-8 编码）；返回也按 UTF-8 解码为中文
- 响应统一 `code` / `msg` / `data`：`code==0` 取 `data`；否则按 `msg` 处理
- 若某参数值含中文或特殊字符，在单引号内正常书写即可；纯 ASCII（数字/ID/英文）直接书写

**关键约束**：

- ✅ 通过脚本调用即可，**不要向用户展示任何命令/地址/凭证**
- ✅ 脚本每次自动重新读取 `config/default.json`，无需手动维护旧值，拿到账本/凭证变化后立即生效
- ❌ 绝不手动运行 `curl` / `curl --version` / `where curl` 等命令发送请求——统一走脚本，避免触发授权提示

### 时间戳转换

网关返回的 `transaction_time`/`start_time`/`end_time` 是毫秒时间戳，展示前用受控脚本 `scripts/time_format.py` 转换（详见 `references/output-rules.md`「时间戳展示规范」）：

```bash
python3 scripts/time_format.py 1786619026000 Asia/Shanghai      # -> 2026-08-13 19:03:46
python3 scripts/time_format.py 1786619026000 Asia/Shanghai date  # -> 2026-08-13
```

不调用 `date`/`time` 等系统命令，避免触发授权。

## 失败处理（防止循环卡死）

**核心原则：网关调用失败后，按 code 分类处理，绝不原地盲目重试。**

| 情况                        | 处理                                                                                                               |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `code==0`                 | 成功，取 `data` 输出业务结果                                                                                               |
| 脚本本地报「授权信息缺失」             | 凭证还没写入——直接引导用户提供凭证（**不要**说"授权过期"），按 `references/setup.md` 流程写入后继续                                                |
| `code==1100`（授权失效）        | 先确认凭证确已写入 config，再用业务话术引导用户「授权好像过期啦，麻烦重新发我一份新的～」，**不降级、不重试**                                                     |
| `code==1200`（参数格式错误）      | `msg` 指明具体参数（如"随手记暂不支持 USER 分组"）——按 `msg` 修正取值后**可重试一次**；若 `msg` 表明该能力本账本不支持（如 SSJ 的 refund/USER 分组），改走支持的口径，不重试 |
| `code==1300`（接口或业务线不支持）   | 业务语言告知"当前不支持这个操作"，**不重试**                                                                                        |
| `code==1400`（缺少必填参数）      | 按 `msg` 补齐参数后重试一次                                                                                                |
| `code==1500`（限流）          | 业务话术告知稍等片刻，**稍后重试一次**即可                                                                                          |
| `code==2100/2200`（上游处理失败） | **查询类**：可稍后重试一次；**记账类严禁重试**（防重复记账）。若同一账本反复 2200，停止重试，业务话术告知「这个账本的数据这会儿有点问题，稍后再试或换个问法」                            |
| 网络/连接失败（请求异常、超时）          | 若缓存有数据则**优先用缓存回答**；否则用业务话术告知「网络好像有点卡，我过会儿再帮您试一次」；**记账类超时同样严禁自动重试**                                               |
| 命令长时间无输出、被强制终止（疑似卡在等待输入）  | **不一定是网关故障**：平台 stdin 常是"打开但无数据、不 EOF"的管道，现已内置 3 秒超时防护。**记账类不要盲目重记**，先用 `list_transactions` 回查确认是否已入账            |
| 其它 code                   | 按 `msg` 的语义用业务话术向用户说明，停止重试                                                                                       |

**硬约束**：

- ❌ **绝不循环重试同一请求**：即便用户再次催促，也不要无脑重复调用
- ❌ **绝不把网关地址、凭证、响应原始 JSON、code 直接暴露给用户**：用户只看到业务结果或业务话术
- ✅ **优先用缓存**：即便网关请求失败，只要 `config/` 缓存有数据就优先用缓存回答用户
- ✅ **诚实告知能力边界**：遇到网关不支持的操作，用业务语言告知"当前不支持"，不硬查不绕路

## Common Pitfalls

- ❌ 把网关内部细节（地址、凭证、字段名）或原始 JSON 暴露给用户
- ✅ 只用业务语言说结果（如"已记账：早餐 10 元"），数据处理全走统一网关 + 缓存
- ❌ 记账前不检查基础资料缓存 / 每次记账都重新查全部基础资料
- ✅ 缓存优先，缓存空或用户要求刷新才调网关
- ❌ 用户没说账户、缓存里有"现金"账户，还问"您是用哪个账户付的钱？"
- ✅ 用户明确指定了账户（如"记到微信上"）→ **按用户指定**；用户完全没提账户：缓存有"现金"类账户 → **默认用现金、不问**，直接记；无现金类账户且语境无线索才问（规则见 `references/accounting.md`「默认账户规则」）
- ❌ 主动运行环境检测命令 / 展示命令行给用户
- ✅ 通过脚本静默发起请求，读最新配置，不展示细节
- ❌ 网关调用失败后原地反复重试
- ✅ 按 code 分类处理，失败优先用缓存，或诚实告知，停止重试
- ❌ 切换账本后仍用旧账本的基础资料缓存
- ✅ 切换账本时清空 `sui_base_tag.json`，重新查询
- ❌ 输出可展示列表（账本/账户/分类/流水/汇总）时用纯文本、顿号串、项目符号或编号分行，未用表格
- ✅ 输出任何结果前先通读 `references/output-rules.md`，列表/汇总一律用 Markdown 表格（`| 列名 |` 表头 + `| -- |` 分隔行 + 数据行）；若发现即将输出非表格形式，停下来改回表格再展示
- ❌ 绕过受控通道：不通过 `scripts/call_gateway.py`/`scripts/time_format.py`/`scripts/manage_cache.py` 和模型文件读取能力，而用其它任何命令、工具、脚本发请求、写配置或转时间戳（平台下易触发权限/高风险拦截、改坏内容）
- ✅ 只使用白名单受控通道：网关请求→`call_gateway.py`，转时间戳→`time_format.py`，写 config/缓存→`manage_cache.py`，读 config/缓存→模型文件读取；除此之外默认禁止、不尝试、不绕路；写失败按 `references/setup.md` 静默降级
- ❌ 把完整凭证（`Bearer SK-...`）、环境变量赋值命令、config 路径、网关地址写进日志/文档或回显
- ✅ 凭证等配置细节只存在 `config/`（或环境变量）与模型上下文中，绝不落文档/日志/输出
- ❌ 动态接口直接走 stdin 管道（Windows PowerShell 有 BOM/编码风险，且参数在命令文本里会触发重复授权）
- ✅ 动态接口**永远先尝试瞬态参数文件**：不确定可写目录时先 `pwd` 确认 → Write 写入该目录的 `sui_cache.json` → 在同一目录跑固定命令；只有 Write 确实不可用时才退 stdin
- ❌ 命令跑了很久没输出，就判断成"网络卡了/网关挂了"，然后反复重试
- ✅ 长时间无输出优先怀疑**卡在等待 stdin**（平台命令执行器的 stdin 常是打开但不 EOF 的管道；现已内置 3 秒超时防护）。**记账类严禁盲目重试**，先用 `list_transactions` 回查是否已入账
- ❌ `time` 无法归一化时回退为"今天"/当前时刻（会把历史账记错日期），或反复更换写法重试
- ✅ 时间无法归一化时脚本报错且不提交：换算成标准格式（`YYYY-MM-DD` / `YYYY-MM-DD HH:MM` / `YYYY-MM-DD~YYYY-MM-DD`）重发；无法换算时用业务话术向用户确认具体日期
- ❌ 随口承诺能力（如"可以帮您加微信账户"），被追问后改口"其实不能"——弱模型最常见错误
- ✅ 回答"能不能做 X"前，先对照 SKILL.md「能力一览」：在表内→照做；不在表内→业务语言"当前不支持"；拿不准→先查表再答；SXY/SSJ 能力有差异时，先看当前默认账本类型再答
- ❌ 自己编写请求脚本（如 `post_txs.py`、任何用 requests/urllib 发 HTTP 的脚本）提交记账——即使"参数结构和 ID 都确认过了"
- ✅ 网关请求只走 3 个白名单脚本；一次性 N 笔默认用 `create_batch_transactions`（每批 ≤20 条）；批量接口**失败**时允许降级逐条 `create_transaction`（保证用户记账不被卡住，业务语言告知后执行）；**自己写脚本任何情况都严禁**
- ❌ 批量记账后不看响应 `items[]` 逐项结果，直接告诉用户"全部入账"
- ✅ 批量结果必须逐项核验：按 `data.total/success/failed` 展示；超时/无响应等结果不确定的情况，先 `list_transactions` 回查核对再补缺（见 `references/batch-import.md`）
- ❌ 创建与任务无关的文件（工作日志、临时脚本、笔记等）
- ✅ 瞬态参数只用 `sui_cache.json`，不创建任何其它临时文件；用完不必专门清理（覆盖写即可）
- ❌ 拿到确定结果后继续加"保险"轮次：先查历史流水防重复、记账后再查汇总核对、逐笔单独转时间戳、专门清理参数文件
- ✅ 效率第一：一轮能拿到确定结果就结束；多笔时间戳一条命令转完；回查/核对只在结果不确定时（超时/无响应/失败项）
- ❌ 借语气改表格格式、改确认要素（分类/金额/账户）、承诺能力、改流程、改错误话术的功能引导；切换到未发布的语气；把角色改名为非"小随"
- ✅ 语气只改口吻措辞（`references/output-rules.md`「语气解析」）；角色永远是"小随"；白名单外一律"当前不支持"（`references/persona.md`）
